## Verification rules and rights

- **README** below means a feature is documented by that repository, *not* independently verified in gameplay. **SOURCE** means a directly examined file confirms a high-level mechanism exists, *not* accuracy/safety. **PROPOSED** is an original ARAM Oracle idea. **TESTED** is never claimed here.
- GitHub public visibility or a README statement "open source" is **not** an explicit grant to reuse code. "MIT verified" below means a root **LICENSE was fetched and says MIT**, not that every upstream dependency, fixture, statistic or asset is MIT. When the LICENSE request returned 404, rights are **UNVERIFIED/NO REUSE** even if the README claims MIT.
- The user specifically wants **ideas rather than copying**, so **do not port code, ranking rules, OCR-match formulas, screenshots, models or UI assets** from any upstream repo. Written notice and independent dependency/data-rights review would be needed for a future separately authorized MIT reuse.
- Mode/game APIs are patch-dependent; local LCU is an unofficial supported-by-context interface, Live Client Data is not proof that augment offers/picked IDs or shop visibility are available. No app here was installed or run. The official [Riot LoL developer guidance](https://developer.riotgames.com/docs/lol) is a separate release gate: in particular, do not assume augment-derived performance scores are compliant just because raw win rates are hidden; do not add automatic game actions or reveal otherwise hidden information.
- Our project is intentionally **PUBLIC**. No private screenshots/crops, Riot IDs, telemetry payloads, logs, secret keys or personal paths may be put in this repository.

## Concrete original takeaways for ARAM Oracle

### A. Functional correctness (F1/F2/F3) — highest priority

1. **Correct self champion vs bench/hover (F1).** Test confirmed local cell, current locked champion, pick intent and old/reordered messages; no fallback to a teammate when ambiguous. The Hex Companion's reported separation of game locale and UI locale is a useful independent acceptance idea. Keep N1 original user-observed fail OPEN until native proof.
2. **Recognize actual offer states and card identity (F2).** Negative tests for no offer, tooltip/shop/dialogue, known vs stale vs unknown, independent L/C/R rerolls, card wrap, scaled HUD, dropped frames and mode-specific exceptional offers. Do **not** weaken our 90/8 margin, epoch or chosen-provider authorization on account of competitor claims. Special offers/4-card layouts require patch evidence before requirements change.
3. **Anvils vs augments (F2 extension).** Build an independent requirements matrix for **stat anvils** and possible distinct card formats. Do not assume every text card is an augment; only add feature after catalog/visibility/policy and specific original tests.
4. **What can I actually buy now? (F3).** Original legal purchase decision must check exact Mayhem catalog, patch, owned components/discount, item recipe, item slot, uniqueness, gold, enemy/ally context, six-item and boots-replacement corner cases. The recommendation should return **one feasible purchase**, not a wish-list of completed items or a fictitious percentage.
5. **Explain counters without fake precision (F3).** Evidence may include directly observed enemy items and champion kit traits, with freshness/uncertainty labels. A heuristic damage mix must never be presented as exact measured incoming damage.

### B. UI, performance and native testing (F4/D6–D8)

6. **Unobtrusive by default.** Champion select -> pre-game comparison; verified augment offer -> three anchored concise decisions; **independently confirmed** shop -> one next purchase; combat -> hidden except explicit user request. A button or tooltip only appears with user intent; do not block game mouse/focus.
7. **Separate brief answer from expansion.** Optionally use a pre-game/desktop-only reference sheet for item recipes, augment combinations, long reasoning and build variants. Avoid recreating competitor panel layouts or click flows.
8. **Performance budget and event throttling.** Independent source freshness and OCR queue cancellation; prevent overlapping scans or repeated scoring on irrelevant frame/timer events, and measure p95 frame/render latency and CPU/RAM/FPS on the user's PC. Upstream marketing benchmarks are not acceptance evidence.
9. **Offline visual replay.** Build our own synthetic game-state + overlay screenshot harness with safe, originally authored fixtures; vary 1080p/1440p, DPI, multiple displays, Alt+Tab, overlay focus, stale/unknown states, rerolls and expiry. Keep test results clearly distinguished from actual native game acceptance.

### C. Trust, interoperability and product polish (later phases)

10. **Never destroy a player's item sets.** If future research approves shop export, explicitly opt-in, stage/preview an isolated set, back up existing sets, validate item IDs, use narrow/idempotent updates with read-back and restore on failure. No bulk overwrite, no purchase automation and no writes during this research.
11. **Human-sized confidence language.** Display `unknown`, `limited sample` or a verified source label instead of invented scores, percentage precision or unlicensed count displays. The fact that a competitor shows `sample size` does not license its data.
12. **Local post-game improvement.** After native core is reliable, a local decision ledger should distinguish *our recommendation*, *user action*, *observed subsequent result* and *unknown/counterfactual*. Do not claim the unavailable path would have produced a win.
13. **No unapproved data reuse.** Audit rights, mode, region, language, patch, source time and denominators before enabling any empirical feed; note data from **normal ARAM cannot silently be labeled Mayhem**.
14. **Installer/updates later.** The portable vs installed distinction, model dependencies, safe update/rollback, signed metadata, user-data retention, per-user install, no forced update mid-match and verified single instance belong to D9–D11, after native/game and policy gates.
